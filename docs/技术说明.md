# 技术说明：权限隔离与"搭建者无法解密"

## 1. 问题定义

需求有三个硬性约束：

1. 服务是 HTTP Web 服务，浏览器打开即用，不是本地脚本；
2. 文本、代码、音视频等 **任意二进制** 文件都要能加密；
3. 不同角色解密权限不同，且 **系统搭建者本人不能解密**。

约束 3 是关键。它的准确含义是：搭建者拥有服务器 root、能读数据库、能看磁盘上的每一个字节，仍然无法还原任何密文。这意味着 **解密所需的密钥材料不能在服务端出现**——不是"不给权限"，而是"根本不存在"。

## 2. V1 对照版：为什么常规做法做不到

V1 的流程是教科书式的：

```
上传文件 ──► 服务端生成 AES-256 密钥 ──► 加密 ──► 密文落盘 + 密钥入库(SQLite files.key_b64)
解密请求 ──► 服务端读库取密钥 ──► 解密 ──► 返回明文
```

它满足约束 1、2，权限层面也做到了"小孔调解密接口返回 403"。但它天然违反约束 3：

- 密钥明文躺在 `data/v1.db` 里；
- 搭建者、运维、拿到数据库备份的任何人，都可以离线解开 **全部** 密文；
- `tests/e2e_v1.py` 的第 4 组测试现场演示了这一点：不登录、直接读库解密成功。

结论：只要加密动作发生在服务端，服务端就必然经手密钥。要满足约束 3，加密必须发生在服务端之外——也就是用户的浏览器里。

## 3. V2 目标版：信封加密（Hybrid Encryption）

直接用 RSA 加密大文件太慢，业界标准做法是 **信封加密**（PGP、age、云厂商 KMS 都是这么做的）：

```
【小孔的浏览器 · 加密】
  ① 随机生成一次性 AES-256 数据密钥（只在内存里）
  ② 用数据密钥加密文件内容          → AES-256-GCM（带认证标签）
  ③ 用"小张的 RSA 公钥"封装数据密钥  → RSA-OAEP-SHA256
  ④ 上传：密文 + nonce + 被封装的密钥

【服务端 · 存储】
  只有：密文(.enc)、nonce、wrapped_key_b64、公钥
  没有：私钥、明文数据密钥、任何能解密的东西

【小张的浏览器 · 解密】
  ① 用口令解开本机的私钥包（PBKDF2-SHA256 250000 轮 + AES-GCM）
  ② 私钥解封 wrapped_key → 得到数据密钥
  ③ AES-GCM 解出原文，SHA-256 校验，本地保存
```

### 为什么每类角色都被正确隔离

| 角色 | 能拿到什么 | 为什么不能/能解密 |
| --- | --- | --- |
| 小孔 | 公钥、密文下载权限被服务端拒绝（403） | 没有私钥；数据密钥被公钥封装，他连封装结果都拿不到 |
| 搭建者 | 密文、nonce、wrapped_key、公钥、全部数据库 | 私钥只在小张本机；RSA-2048 在现有算力下不可暴力破解 |
| 小张 | 密文 + wrapped_key + 自己的私钥包 | 唯一持有私钥的人，解密全程在本地完成 |

### 密钥包的 protects 什么

小张的私钥以 PKCS#8 导出后，用他的口令做 PBKDF2-SHA256（250,000 轮）派生 AES-256 密钥，再 AES-GCM 加密成 `小张-私钥包-日期.key.json`。因此：

- 私钥包文件丢了 → 没有口令的人拿不到私钥；
- 口令泄露但文件没丢 → 同样解不开；
- 私钥 **从不上传**，服务器端的 `/api/keys/public` 只保存公钥（公开信息）。

### 防篡改与绑定

- AES-GCM 自带认证标签：密文被改 1 位，解密直接失败；
- GCM 的 AAD 绑定了文件名，改名后的密文无法解密；
- 客户端对密文计算 SHA-256，服务端校验，防止传输损坏；
- 私钥包用 AES-GCM 加密 + AAD 绑定用途字段。

## 4. 服务端自证机制

V2 内置两个"自证"接口，演示时可以现场点：

- `GET /api/proof/schema` —— 返回 `files` 表全部字段，并标注哪些字段含机密。结论是 `secret_columns: []`：库里只有 `wrapped_key_b64`（被公钥封装的密钥），没有私钥字段；
- `POST /api/proof/server-decrypt/{id}` —— 让服务端尝试解密，固定返回 **501**，说明缺的是私钥而不是权限。

另外 `tests/e2e_v2.mjs` 覆盖了：全链路还原一致性、小孔 403、服务端 501、错误口令拒绝、别人的私钥解不开、密文篡改被 GCM 识别。

## 5. 二进制文件的处理

两个版本都 **以字节流为单位** 读写（FastAPI `UploadFile` → `bytes` → AESGCM），从不把文件当字符串解码。这是 `.docx`、`.mp3`、`.mp4` 这类压缩容器/媒体流能够无损往返的原因；`test_files/` 里 8 种格式就是用来验证这一点的，演示后可用 SHA-256 对比原文与解密结果。

## 6. 已知边界与可选增强

本项目定位是课程/演示级实现，以下边界是 **有意保留** 的简单性：

| 边界 | 说明 | 生产环境建议 |
| --- | --- | --- |
| 文件名、大小等元数据明文存储 | V2 保护内容，不隐藏元数据 | 元数据也加密，仅存序号 |
| 会话在单进程内存中 | 重启服务需重新登录 | Redis / JWT |
| 大文件全量读入内存 | 200MB 上限内可用 | 分块加密 + 流式上传 |
| 口令无找回机制 | 私钥包 + 口令丢失 = 文件永久无法解密 | 门限恢复 / 密钥托管策略 |
| 无速率限制、无验证码 | 演示环境 | 反爆破、登录限流 |

## 7. 运行环境

- Python 3.10+（验证环境 3.13），依赖仅 `fastapi / uvicorn / cryptography / python-multipart`；
- 前端零第三方依赖：原生 HTML/CSS/JS + 浏览器内置 Web Crypto；
- 测试脚本用 Node 18+（内置 Web Crypto 与浏览器同一套 API）。

## 8. 合规提示

系统使用的 AES-256-GCM、RSA-OAEP、PBKDF2 均为公开国际标准算法（RFC 3394/8017、NIST SP 800-38D），用于合法的数据保密教学演示。请勿用于违法用途。
