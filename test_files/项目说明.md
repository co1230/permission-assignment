# 加密演示 · 测试素材说明

这份 Markdown 用来验证「文本类文件」在加密—解密往返后**逐字节一致**：
标题层级、列表、表格、代码块、中英文混排、标点符号都必须原样保留。

## 文件清单

| 文件 | 类型 | 用途 |
| --- | --- | --- |
| `项目说明.md` | Markdown 文档 | 验证 UTF-8 文本与格式完整还原 |
| `demo_code.py` | Python 代码 | 验证缩进、注释、中文 docstring 不被破坏 |
| `demo_code.js` | JavaScript 代码 | 验证另一种语言的源码文件 |
| `会议纪要.docx` | Word 文档 | 验证 Office 压缩包类二进制文件 |
| `数据统计.xlsx` | Excel 表格 | 验证表格类二进制文件 |
| `演示报告.pdf` | PDF 文档 | 验证 PDF 二进制文件 |
| `测试音频.mp3` | 音频 | 验证媒体流文件（含 ID3 元数据） |
| `演示视频.mp4` | 视频 | 验证较大的二进制容器文件 |

## 为什么二进制文件也要测

AES 加密的是字节流，不是"字符串"。
如果把文件当文本读进来再加密，`.docx`、`.mp3`、`.mp4` 会在编码转换时损坏——
即使解密成功，文件也打不开了。因此两个版本都必须以 **二进制模式** 读取与写出。

## 校验方法

演示结束后，用 SHA-256 对比原文件与解密出的文件：

```bash
# Windows PowerShell
Get-FileHash .\test_files\测试音频.mp3 -Algorithm SHA256
Get-FileHash .\下载\测试音频.mp3 -Algorithm SHA256

# macOS / Linux
shasum -a 256 test_files/测试音频.mp3
shasum -a 256 ~/Downloads/测试音频.mp3
```

两个哈希完全相同，说明加解密无损。

## 一段中文混排与标点

端到端加密的意义在于：**服务器只保管看不懂的东西**。
引号「」、破折号——、省略号……、全角逗号，以及 English words mixed in，都应该一模一样。
换行符也保持一致；不要因为加密而改变文件的任何一位。

> 如果这段文字在解密后有任何字符变化，说明实现用了文本模式读写，需要改成二进制模式。
